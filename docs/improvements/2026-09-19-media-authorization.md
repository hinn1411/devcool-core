# Improvements — Media Endpoint Authorization

**Date:** 2026-09-19
**Scope:** `adapters/in/web/controller/MediaController.java`, `application/service/MediaService.java` (pre-existing, not introduced by `feat/list-messages-in-a-chat-room`)

---

## High

### 1. `GET /api/v1/medias/presigned-url` has no authorization check
**Files:**
- `adapters/in/web/controller/MediaController.java` (`getPresignedUrl`)
- `application/service/MediaService.java` (`getPresignedUrl`)

The endpoint takes any `key` and signs it with no authorization check. Any logged-in user can get a URL for any object in the bucket. Someone who left a channel can keep opening its media forever if they saved the keys.

**Must be fixed before** moving the message list to "return S3 key only; the client calls the presigned-url endpoint" (option C in the "Service mutates domain objects in place" discussion). Under that design this endpoint controls all access to media.

**Fix options:**

1. **Parse the channel from the key (simple).** Keys have the format `channel/{channelId}/{yyyy/MM/dd}/{uuid}{ext}`.
   - Pass `userId` from `Authentication` into the use case, the same way `MessageController.getMessages` does.
   - In `MediaService.getPresignedUrl`, extract `channelId` from the key and reject keys that don't match the format with `InvalidObjectKeyException`.
   - Reuse `MemberPort.findMemberOfChannelByUserId(channelId, userId)` and throw `MemberNotFoundException` (mapped to 403) if it's empty. This is the same check `MessageService.getMessages` uses.
   - This is safe **only because keys are always generated by the server**, today in `MediaService.buildMediaKey`. If clients can ever supply or choose keys, use option 2.

2. **Look the key up in the DB (stricter).** Resolve key → `MediaEntity` → message → channel, then check membership.
   - This proves the key belongs to a real, non-deleted message. A key that was uploaded but never attached to a message gets 404.
   - It needs a media outbound port, such as `MediaPort.findChannelIdByPath(String path)`, and ideally an index on `MEDIA.PATH`. The old `MediaPort`/`MediaAdapter`/`MediaRepository` were deleted as dead code, so this fix has to bring back the port, the adapter and a Spring Data repository with this query.

**Also consider:** a batch variant, `POST /api/v1/medias/presigned-urls` with `{ keys: [...] }`, so a chat screen doesn't make one request per image. Apply the same authorization to every key in the batch.

## Related

### 2. `POST /api/v1/medias/upload` does not check channel membership
`MediaService` only depends on `MediaStoragePort`, and `upload` never checks that the caller belongs to `channelId`. Any logged-in user can upload files under another channel's `channel/{channelId}/...` prefix.

**Fix:** pass `userId` (already in `UploadMediaCommand`) through the same membership check as #1 before calling `storagePort.upload`.
