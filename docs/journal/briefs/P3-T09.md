# P3-T09 — Reactions
P3 · mode A · Could · est 5h · agreed · 2026-11-12

**Why:** a message can't carry a lightweight response. The ERD plans `MESSAGE_REACTION` (`03-chat-system-design.md:41`); no table, port or endpoint exists, and `MessageItem` (`domain/chat/model/MessageItem.java`) has no reactions.
**Value:** phase goal "Replies and reactions". Unblocks P4-T04 (`REACT` frame → `REACTION` broadcast), P5-T05/T07 (reaction UI).

## Concepts
- **PK as the idempotency key:** without: two concurrent PUTs both see "not reacted" and insert → count 2. With: PK `(message_id, user_id, emoji)` + `INSERT … ON CONFLICT DO NOTHING` → one row, no lock. Read: `docs/references/05-postgresql-and-data-access.md` (`ON CONFLICT`).
- **Identity from the token:** without: a `userId` in the request lets Bob remove Alice's 👍. With: `user_id` comes only from `Authentication`, so "undo another member's reaction" can't be expressed.
- **One grouped query per page:** without: a lookup per `MessageItem` → 50 queries for 50 messages. With: `SELECT message_id, emoji, count(*), bool_or(user_id = :me) … WHERE message_id IN (:ids) GROUP BY 1, 2`, merged in memory; the PK prefix serves it.
- **Non-member = not found:** without: 403 vs 404 lets a caller probe message ids. With: `MessageNotFoundException` as in `DeleteMessageService.java:50`.

## Done when
1. A member PUTs an emoji → one row, 204; history shows `{emoji, count: 1, reactedByMe: true}`. A repeated PUT → still 1, 204.
2. Two concurrent PUTs (same user, message, emoji) → exactly one row.
3. Two users, same emoji → count 2; different emojis → separate entries, ordered by the first reaction's `created_time`.
4. DELETE removes only the caller's row → 204; other users' counts stay. DELETE with no row → 204 no-op.
5. Non-member, unknown or deleted message → 404 on PUT/DELETE, nothing written; history shows `[]` for a tombstone or no reactions.
6. Invalid emoji (a non-emoji code point, blank, or > 16 code points) → 400.
7. Each of the 3 history queries adds exactly one reactions query per page (statement-count IT).
8. A 21st distinct emoji on a message → 409; an emoji already on it still works.
- **Out of scope:** `REACTION` WS broadcast (P4-T04), reaction notifications (P6), rate limiting, single-grapheme / VS16 normalization.
- **Tests:** `EmojiTest`, `ReactionServiceTest`, `MessageServiceTest` (history), `ReactionAdapterIT` (idempotency, order, statement count), `MessageReactionIT` (HTTP matrix, 20-thread race, cap), `MessageDtoMapperTest`.
- **Invariants / authz:** emoji (400) → message live + caller a member (404) → cap (409) → own row only.

## Decisions
| Question | Answer | Source |
|---|---|---|
| Emoji validation | Code points `Character.isEmoji` or ZWJ/VS16/keycap, ≥ 1 emoji, ≤ 16; bare `1` passes | user |
| DELETE with no row | 204 no-op (idempotent, toggle semantics) | user, phase design notes |
| Deleted message | PUT/DELETE → 404; history tombstone → `reactions = []` | user |
| `reactedByMe` | Included, via `bool_or` in the same grouped query | user |
| Body / index | 204, no body (live update in P4-T04); no extra index, the PK leads with `message_id` | phase scope, P3-T02 |
| Distinct-emoji cap | 20 per message → 409 `MESSAGE_412`; check-then-insert, may overshoot slightly | security review |
| FK `ON DELETE` | None: deletes are soft; revisit with P6 erase | hexagonal review |
