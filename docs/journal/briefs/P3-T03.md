# P3-T03 — seq assignment + idempotent send
P3 · mode A · Must · est 5h · agreed · 2026-11-05

**Why:** `AbstractMessageCreationStrategy.java:24` saves without `seq`/`clientMsgId`; `WsClientFrame.java:10` carries the key but nothing uses it ([learning/04](../../learning/04-concurrency-and-realtime.md)) → a retry on a lost ACK stores a duplicate, and clients can't spot a gap.
**Value:** phase goals "Ordering" + "Idempotent send" ([ADR-0012](../../plans/architecture/adr/0012-message-ordering-per-channel-seq.md)) → M2 (survive a deploy needs resume by seq). Unblocks P3-T03a, T04, T05, T10, P4 RESUME.

## Concepts
- **Row-lock counter:** without: two members post in #general together, both read MAX(seq)=41, both write 42 → collision. With: `UPDATE channel … RETURNING last_seq` locks the row; the second waits and gets 43. Read: ref 05 "Row locks serialize writers", ADR-0012.
- **Idempotency key:** without: ACK lost on flaky wifi, client resends → the same text at seq 42 and 43. With: the `(user_id, client_msg_id)` lookup hits → returns 42, `last_seq` stays 42. Read: ref 02 "Idempotency keys".
- **Check-then-act race + aborted tx:** without: two retries both miss the SELECT; the 2nd INSERT hits `uk_message_user_client_msg` → error to the user. With: Postgres rolls back the 2nd tx (its bump too); the caller re-reads in a **new** tx → same seq. Read: learning/04 §1, ref 05 "ON CONFLICT".

## Done when
1. Given an empty channel, when a member sends with a new key, then `seq=1`, `last_seq=1`, `last_message_at` set; save returns `SavedMessage(id, seq, createdTime)`.
2. Given seqs 1..n, when a member sends, then the new message gets n+1 from `channel.last_seq`, not from reading the message table.
3. Given a saved message with key K, when the sender resends K to the same channel, then the same id+seq come back, `last_seq` is unchanged, there's one row, and nothing is re-broadcast.
4. Given two concurrent sends with key K, then both return the same id+seq, there's one row, and `last_seq` moved once.
5. Given 20 parallel sends with distinct keys to one channel, then the seqs are exactly 1..20 and `last_seq=20`.
6. Given a SEND frame with a missing or non-UUID `clientMsgId`, then an ERROR frame comes back, the socket stays open, nothing is saved, no bump.
7. Given a non-member, then rejected before any bump (`last_seq` unchanged).
8. Given key K already used in channel A, when the sender sends K to channel B, then rejected with an ERROR frame, no bump, no row.
- **Out of scope:** NOT NULL on seq (T03a) · `messageId`/`seq` in the ACK and push (T04) · history by seq (T05) · sender's own `last_read_seq` bump in the send tx (T10) · outbox row (P6).
- **Tests:** unit `MessageServiceTest` (first send, hit skips the bump, race re-read, key reuse in another channel) · IT 20-parallel → 1..20 · IT retry race · handler test for missing/invalid key · `MessageAdapterIT` maps `seq`/`client_msg_id`.
- **Files:** `CreateMessageCommand`, `SendMessageCommand`, `SaveMessageUseCase` (→ `SavedMessage`), `MessageService`, strategies, `MessagePort`/`ChannelPort` + adapters, `MessageEntity`, `RawWebSocketHandler`, `WsSendMessageService`.
- **Invariants / authz:** order = authz → key lookup → bump → insert; a retry never bumps; the re-read after a violation runs in a new tx.
