# P1-T16 — Enable virtual threads
P1 · mode A · Must · est 3h · done · 2026-10-10

**Why:** Tomcat serves HTTP and WS frames from 200 platform threads; each `SEND_MESSAGE` holds one through a JDBC insert and a sequential socket fan-out (`WsSendMessageService:43-47`) → in a burst, frames queue behind blocked threads ([03](../../plans/architecture/03-chat-system-design.md) sizes for 3,000 peak sockets).
**Value:** cheap blocking for JDBC/S3/WS writes now, Bedrock later ([02-tech-stack:11](../../plans/architecture/02-tech-stack.md)) → P1 deployable base → M1. Unblocks the P4 delivery executor ([03 §6](../../plans/architecture/03-chat-system-design.md#6-fan-out-across-nodes)), P7 virtual-thread metrics, interview Q17.

## Concepts
- **Virtual threads:** without: 250 users send at once, 200 threads stuck in INSERT/socket writes, 50 frames queue. With: each frame gets a cheap thread; a blocked one unmounts and frees its carrier. Read: [ref 10](../../references/10-spring-boot-and-java-runtime.md) Concepts, JEP 444.
- **Pinning (Java 21):** without: a socket write inside `synchronized` keeps the carrier (≈1 per core) → 4 slow clients freeze a 4-vCPU task. With: a `Semaphore`/`ReentrantLock` guards the write (Tomcat 10.1.46 `WsRemoteEndpointImplBase` already does) → it unmounts. Read: JEP 491, Oracle guide (JFR).
- **The bottleneck moves:** without: "virtual = unlimited", 1,000 sends race for Hikari's 10 connections → fail after `connectionTimeout` 30 s. With: the pool size stays the deliberate cap on DB concurrency. Read: ref 10 bulkhead.
- **Test thread ≠ server thread:** without: MockMvc asserts `isVirtual()` but runs on the JUnit thread → proves nothing. With: `RANDOM_PORT` + a real socket runs on Tomcat's executor.

## Done when
1. Given `spring.threads.virtual.enabled=true` in `application.properties` (all profiles), when a WS frame arrives over a real socket, then the handler runs on a virtual thread.
2. Given two clients in one channel sending at once, then a JFR `RecordingStream` (`jdk.VirtualThreadPinned`, threshold 0) records zero events.
3. The audit (app `grep synchronized` + Tomcat `javap`: monitors only guard queue ops and `tryAcquire`) is written in the PR.
- **Out of scope:** concurrent-send safety / `ConcurrentWebSocketSessionDecorator` (P4-T01), bounded delivery executor (P4), Hikari tuning + virtual-thread metrics (P7).
- **Tests:** new `WsVirtualThreadsIT` (`RANDOM_PORT`, `StandardWebSocketClient`, JWT in handshake) asserts 1 and 2; P1-T15 MDC tests stay green.
- **Files:** `src/main/resources/application.properties`, `src/test/java/com/devcool/adapters/in/websocket/WsVirtualThreadsIT.java`, phase-1 checkbox.
- **Risk:** localhost writes rarely block, so zero JFR events is a regression guard, not a proof; the `javap` audit is the primary evidence.
