# P3-T01 — Ids INTEGER → BIGINT
P3 · mode A · Must · est 4h · agreed · 2026-10-26

**Why:** every PK/FK is `integer` (`V1__baseline.sql:4`) and every Java id is `Integer` → any table's next insert fails at id 2,147,483,647. `ALTER TYPE` rewrites the table under an `ACCESS EXCLUSIVE` lock: milliseconds on today's smoke data, minutes once `message` is big.
**Value:** P3 goal "the data model realtime and events need" ([03 §2](../../plans/architecture/03-chat-system-design.md)). Phase Risks: "do it first, alone, in one PR". Unblocks P3-T02 (`seq`, `last_seq` as BIGINT next to BIGINT ids) and everything after.

## Concepts
- **`ddl-auto=validate`:** without: V3 ships, `MessageEntity.id` stays `Integer` → the migrate task and new tasks fail at startup ("wrong column type"). With: V3 + `Long` entities in one image; ITs prove they match. Read: `docs/references/05-postgresql-and-data-access.md` § Migrations as code.
- **Mixed versions in a rolling deploy:** without: fear that old tasks break after the migrate task widens the columns. With: they keep working (a bigint < 2³¹ reads as an int), so no expand/contract. Read: `.claude/rules/flyway.md`.
- **DDL lock:** without: `ALTER` waits behind a long transaction and every request queues behind it. With: `SET lock_timeout = '5s'` → fails fast, deploy stops before rollout. Read: `docs/learning/11-flyway-and-schema-management.md` §7e.
- **Silent type traps:** without: `WsAuthHandShakeInterceptor.java:27-32` checks `Integer.class::isInstance` → a `Long` principal compiles and every WS handshake is rejected. With: a WS IT covers it. Same family: `(Integer)` casts (`RawWebSocketHandler.java:115`), JsonPath returning `Integer` in ITs.

## Done when
1. Given V1–V3 applied, then no PK/FK column is `integer` (`information_schema` assertion) and history includes V3.
2. Given the sequences set beyond 2³¹, when a user registers, logs in, creates a channel, sends over WS and reads history, then every id round-trips as a `Long`. This proves the scale goal.
3. Given old tasks running, when the migrate task applies V3, then they keep serving and the new tasks pass `validate`.
4. Non-id Integers unchanged: `token_version`, `total_of_members`, limits, enum codes, counts.
- **Out of scope:** seq/version columns (P3-T02), the frontend (P5, generated types), `refresh_token.user_id` varchar with no FK (debt; not integer, so it can't overflow).
- **Tests:** existing suites updated (~26 files: `1L`, `anyLong()`, JsonPath `Number`); a new IT for criteria 1–2; `./mvnw -Dit -Pstatic-analysis verify`; the CD migrate task green on Aurora.
- **Files:** `db/migration/V3__ids_to_bigint.sql`, ~100 files in `src/main/java` (domain → application → adapters), tests, ADR-0012 (done), phase-file tick.
