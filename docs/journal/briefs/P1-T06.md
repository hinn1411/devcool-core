# P1-T06 — Channel update and add-member authorization
P1 · mode A · Must · est 4 h · done · 2026-10-01

**Why:** `ChannelController.java:57-75` takes no `Authentication`, and `ChannelService.updateChannel`/`addMember` never ask who is calling. Any logged-in user can add themselves to any channel, which then satisfies the correct membership checks in `MessageService.java:66` and `WsSubscribeService.java:34` (`docs/learning/02-security-and-authorization.md` §4, audit #4 and #5).
**Value:** closes audit rows #4 and #5 → P1 Definition of Done. Feeds P1-T12 (authz ITs), the "role table" P3 builds on (`phase-3-core-chat.md:36`, P3-T07, P3-T11) and M4 ("never leaks a private channel").

## Concepts
- **Guard the grant point:** without: Eve posts `{"userIds":[eve]}` to a DM's `/members` and reads the whole chat. With: 403, because Eve isn't a member of that channel. Read: `learning/02` §4.
- **Check order is exists → allowed → work:** without: user ids are validated first, so a non-member learns which ids exist. With: 404, then 403, before any other work. Read: `.claude/rules/hexagonal.md`.
- **Authorization vs validation:** "who may do this" (403) and "is this change legal for a FORUM" (422) are different rules with different tests. Read: `docs/references/11-security.md` §Concepts.
- **A role table, not scattered ifs:** without: P3-T07 and P3-T11 re-derive "who is an admin". With: one `(channelType, role) → allowed actions` policy they reuse.

## Done when
1. The role table holds: LOUNGE: any member may update and add. FORUM: only `CREATOR`/`LEADER` may update and add. PRIVATE_CHAT: either participant may update; nobody may add.
2. Given a non-member, when PATCH or add-member, then 403 and nothing is written.
3. Given a FORUM `MEMBER`, when PATCH or add-member, then 403.
4. Given a PRIVATE_CHAT, add-member returns 422 for every caller; a LOUNGE never exceeds 11 people.
5. A missing channel returns 404 before any 403; the controller passes the caller's id from `Authentication`.
- **Out of scope:** update-field validation (type toggling, expired time > now + 7 days, no expiry on FORUM): new task P1-T18; authz ITs with real tokens (P1-T12); remove/leave/transfer leader (P3-T11); `permitAll` on `/channels` (P1-T09); a FORUM total cap (P3-T11).
- **Tests:** unit tests per caller kind (non-member, member, creator, leader) × action × channel type, written by you first for each rule; a controller slice test that the caller id reaches the use case; `@Size(max = 50)` on the request.
- **Files:** `ChannelController`, `AddMembersRequest`, `UpdateChannelUseCase`, `ChannelService`, new policy class and `ForbiddenException` in `domain/`, `MemberPort` + `MemberAdapter` (role lookup), tests; docs: `03-chat-system-design.md:228`, phase design note `:53`, new P1-T18 line.
- **Invariants / authz:** every check runs in `ChannelService` before any write; role and channel type are read from the DB, never from the request.
