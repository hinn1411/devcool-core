# P1-T03 — Message history index `(channel_id, id DESC)`
P1 · mode A · Must · est 2h · agreed · 2026-10-04

**Why:** `V1__baseline.sql` has no secondary indexes, so `message.channel_id` is unindexed. The history query (`MessageRepository.java:18-21`) scans all channels' messages, or walks `pk_message` backwards and filters by channel, to return 51 rows. The cost grows with total messages, not with the page size.
**Value:** history reads proportional to the page size → P1 "safe before building on it". It is the evidence for playbook §5.2 game day 4 ("slow history page"). P3-T02 later replaces it with `(channel_id, seq DESC)`.

## Concepts
- **Composite ordered index:** without: opening #general (50k of 1M messages) → filter and sort across every channel. With: seek to `channel_id = 7`, read newest first, stop after 51 rows. Read: ref 05 "Keyset (seek) pagination".
- **Catch-all predicate:** without: `(:cursorId IS NULL OR id < :cursorId)` under a generic cached plan → the cursor is a filter, not an index bound, so page 100 walks past 5k newer rows. With: one query per case → `id < :cursorId` becomes an `Index Cond`. Not fixed here (decision below).
- **EXPLAIN on realistic data:** without: 20 local rows → Seq Scan, and the index looks "useless". With: ~100k seeded rows + `ANALYZE` → `EXPLAIN (ANALYZE, BUFFERS)` shows an Index Scan and no `Sort`. Read: ref 05 "Using EXPLAIN".
- **Index build lock:** a plain `CREATE INDEX` blocks writes to `message` during the build. That's fine pre-P2 (no deployed DB). Later migrations need `CONCURRENTLY` plus a non-transactional Flyway script.

## Done when
1. Given an empty DB (`docker compose down -v`), when the app starts on `local`, then Flyway applies V1+V2 and Hibernate's `validate` passes.
2. Given ~100k messages across several channels and `ANALYZE`, when I EXPLAIN the history SQL with literal values for a quiet channel, then the plan is an Index Scan on `ix_message_channel_id_id` with no `Sort` node. A hot channel may keep `pk_message` backward (decision below).
3. The before/after EXPLAIN output is in the PR and the journal. Also capture the cursor query under `SET plan_cache_mode = force_generic_plan` to document the catch-all risk for P3-T05.
- **Out of scope:** splitting the catch-all query (P3-T05 rewrites history on seq); the automated repository IT (P1-T12, after P1-T11); dropping this index once `cursorId` is removed (P3-T05+).
- **Tests:** manual EXPLAIN evidence (above); the automated IT is in P1-T12.
- **Files:** `src/main/resources/db/migration/V2__message_channel_id_index.sql`; the P1-T03 line in `docs/plans/phases/phase-1-foundation-hardening.md` (rename the file reference, tick the task).
