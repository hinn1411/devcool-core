# P3-T11 — Member management: remove, leave, transfer leader
P3 · mode A · Must · est 5 h · done · 2026-11-16

**Why:** membership only grows today: `ChannelAction` has just `UPDATE_CHANNEL, ADD_MEMBERS` (`domain/channel/policy/ChannelAction.java`), and [03 §12](../../plans/architecture/03-chat-system-design.md) leaves removal "defined in P3-T11". Without this task, a kicked or departing user keeps reading and posting, and a Forum can never change its leader.
**Value:** the last role-based management item in the P3 goal (phase-3 §Goal) → M1. P4 builds on it: a SUBSCRIBE or RESUME from a removed user must fail. P3-T12 relies on a DM keeping both members.

## Concepts
- **Hard-delete the member row, keep the content:** without it, a soft-deleted member blocks `uk_member_channel_user` (V1:79), so a later re-add fails. With it, the row is deleted, messages, media and reactions stay, and a re-add starts caught up (`MemberPort.addMembers`, `last_read_seq = last_seq`).
- **Lock the channel row before checking:** without it, 20 parallel adds all read `total_of_members = 10` and the Lounge passes 11, or a leave deletes the member a racing transfer just made leader. With it, `requireAllowedForUpdate` reads `FOR NO KEY UPDATE`, so the checks hold until commit (`MemberManagementConcurrencyIT`). Read: `docs/references/05-postgresql-and-data-access.md` § row locks.
- **Leader invariant:** without it, a leader who leaves makes the Forum leaderless, so only the CREATOR can manage it and `channel.leader_id` goes stale. With it, the leader must transfer first, and the transfer swaps both roles and `leader_id` atomically.
- **Authn ≠ authz on every path:** without it, a removed user's token still works on `GET /messages`. With it, every channel service goes through `ChannelAuthorizer`, so the removed user gets 403 everywhere. Read: `docs/improvements/lessons.md` (membership rule).

## Done when
1. Given a Forum CREATOR/LEADER or a Lounge CREATOR, when they call `DELETE /channels/{id}/members/{userId}` on a MEMBER, then 204: the row is gone, `total_of_members` drops by 1 and the target's messages stay.
2. Given a caller who is not allowed (a Lounge MEMBER, a Forum MEMBER, a PRIVATE_CHAT member), when they remove someone, then 403, or 400 for PRIVATE_CHAT (unsupported).
3. Given any target who is the CREATOR, or the caller themselves, when someone tries to remove them, then 400. A target who isn't a member → 403 `MEMBER_NOT_FOUND` (`HttpErrorMapper:35`).
4. Given a member who isn't the leader, when they call `DELETE /channels/{id}/members/me`, then 204 and the count drops by 1. A Forum leader → 400 (transfer first). PRIVATE_CHAT → 400. A non-member → 403.
5. Given the current Forum leader, when they call `PUT /channels/{id}/leader {userId}` naming a member, then the target becomes LEADER, the old LEADER becomes MEMBER (a CREATOR-leader stays CREATOR) and `leader_id` = target.
6. A transfer from a caller who isn't the leader → 403. Self or a non-member target → 400/403. A non-Forum channel → 400.
7. Given a removed user, when they call history, send, read marker, react, edit or presign on that channel, then 403 or 404 (the existing rule per path).
- **Out of scope:** dropping a removed user's live WS subscription (P4), CREATOR transfer, deleting an empty channel, member-list endpoint.
- **Tests:** unit: `MemberManagementServiceTest`, `ChannelPermissionPolicyTest` · IT: `ChannelControllerAuthzIT` nests (1–7), `MemberManagementConcurrencyIT` (lounge cap, transfer vs leave).
- **Invariants / authz:** a Forum always has exactly one leader. `total_of_members` = member row count. Every check order: channel exists (404) → caller is a member (403) → action supported (400) → role allowed (403).

## Decisions
| Question | Answer | Source |
|---|---|---|
| API shape | Resource endpoints (DELETE member, DELETE members/me, PUT leader) | user; matches `ChannelController` POST /members |
| Who removes | Forum CREATOR/LEADER, Lounge CREATOR; PRIVATE_CHAT unsupported; the CREATOR can't be removed | user; mirrors `MessageDeletePolicy` |
| Leave | Everyone except the Forum leader (transfer first) and PRIVATE_CHAT members | user; narrows 03 §12 "any member can leave"; 03 §12 updated |
| Transfer caller | Current leader only (`leader_id`) | user |
| Removed user's content | Kept; the row is hard-deleted so a re-add works | user + V1:79 |
| Remove the Forum leader | 400, transfer first (keeps one leader) | user, at Red |
| Races (review) | Add/remove/leave/transfer lock the channel row first (`FOR NO KEY UPDATE`); also fixes the pre-existing Lounge cap race | review, user approved |
