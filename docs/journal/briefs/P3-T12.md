# P3-T12 — DM convenience: find-or-create a private chat
P3 · mode A · Could · est 3 h · done · 2026-11-17

**Why:** every `POST /channels` PRIVATE_CHAT inserts a new channel (`PrivateChatCreationStrategy.java:40`); no pair constraint in the schema (`V1__baseline.sql:47`) → each "Message" tap in P5 opens another empty DM.
**Value:** one "open DM" call for the P5 UI (→ M3); relies on P3-T11 (PRIVATE_CHAT members can't leave, so a pair stays two members).

## Concepts
- **Normalized pair key:** without: A→B and B→A each pass a `(caller, target)` check → two DMs. With: `(LEAST, GREATEST)` gives both one key, one row. Read: refs/05 § `ON CONFLICT`.
- **Constraint-backed find-or-create:** without: two concurrent calls both find nothing and both insert. With: the PK rejects the loser, which catches the violation and re-reads (P3-T03 pattern in `MessageService`).
- **Backfill before the constraint:** existing duplicate DMs would break the key; the migration indexes only the oldest channel per pair (expand/contract, P3-T02/T03a).

## Done when
1. No DM for the pair → PRIVATE_CHAT created with both members, `direct_chat` row inserted → 201 + channel id.
2. DM exists, called from either side → 200 + same channel id, no new rows.
3. 10 parallel calls for one pair → exactly one channel and one `direct_chat` row.
4. Target = caller → 400; target missing, DELETED or BLOCKED → 404 (an existing DM is still returned).
5. `POST /channels` with PRIVATE_CHAT goes through the same find-or-create → no duplicate.
6. Migration on a DB with duplicate DMs: oldest channel per pair indexed, others left as-is.
- **Out of scope:** friendship requirement (no friend domain yet), merging duplicate DMs, group DMs, DM-creation rate limit (P4-T13).
- **Tests:** `DirectChatServiceTest` (create, hit both orders, self, missing/inactive), `DirectChatConcurrencyIT`, `V9DirectChatBackfillIT`, `ChannelControllerAuthzIT` (unauthenticated → 401, legacy path).
- **Files:** `V9__direct_chat.sql`, `domain/channel/port/{in,out}`, `application/service/channel/`, `PrivateChatCreationStrategy`, `ChannelController`, persistence adapter.
- **Invariants:** ≤ 1 PRIVATE_CHAT per unordered pair; `user_low_id < user_high_id`; the caller is always one of the pair.

## Decisions
| Question | Answer | Source |
|---|---|---|
| Pair storage | `direct_chat(user_low_id, user_high_id, channel_id UNIQUE)`, PK on pair, CHECK low < high | user |
| Legacy `POST /channels` PRIVATE_CHAT | Routed to find-or-create | user |
| Status | 201 created / 200 existing | user |
| Inactive target | 404 like missing; existing DM still returned | user |
| Legacy path responses | Existing DM still 201; self stays `USR_405` (`/direct` gives 200 and `CHANNEL_400`) | review |
| Race handling | `ON CONFLICT DO NOTHING` + rollback-only + re-read in one tx, not catch-and-retry: no tx abort, READ COMMITTED sees the winner | build |

## Prediction gaps
- "One per (callerId, friendId)" → the pair is unordered (*knowledge gap*: refs/05 § unique constraints).
- No concurrency case → simultaneous taps need constraint + catch-and-re-read (*knowledge gap*: ADR-0012 / P3-T03 race).
- Existing duplicates in the migration (*knowledge gap*: phase-3 Risks, expand/contract).
- "Friend" → no friendship in code; any active user (*open*, decided: out of scope).
