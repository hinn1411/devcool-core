# P4-T01 — Safe per-session writes (decorator + cleanup)
P4 · mode B · Must · est 3–4 h · agreed · 2026-11-26

**Why:** every write hits the raw session (`FrameWriter.java:30-32`; actions get it from `ChatHandler.java:94`), and the fan-out runs on the sender's thread (`SendMessageService.java:47`) → one stalled phone delays the whole channel, and concurrent writes garble frames (`docs/learning/04` §2).
**Value:** Stage 1 hardening the backplane builds on (`learning/10` §7) → M2 "slow client" drill, interview Q18. Unblocks T02 (dispatcher writes through it), T08 (listener pushes through it).

## Concepts
- **Serialized writes:** without: Alice's ACK (her thread) + Bob's push to Alice (his thread) hit her socket at once → `IllegalStateException TEXT_PARTIAL_WRITING`. With: the 2nd writer enqueues; the lock holder flushes in order. Read: `learning/04` §2.
- **Bounded buffer + TERMINATE:** without: Bob in a tunnel → fan-out waits on him → Carol delayed. With: Bob's writes queue up to 512 KB / 5 s, then `SessionLimitExceededException` → server closes Bob with 4500 → he reconnects and resumes (T09). Read: `docs/references/03` §Backpressure.
- **Decorator never closes itself:** the exception is a `RuntimeException`; `SessionEmitterAdapter.java:35` doesn't catch it → it escapes and breaks the loop for Carol. The caller must `close()` (verified in spring-websocket 6.2.19 bytecode).
- **Lock holder still blocks:** the 5 s limit is checked only when *another* send arrives; the flushing thread sits in Tomcat's blocking write (default 20 s). Fix: `org.apache.tomcat.websocket.BLOCKING_SEND_TIMEOUT=5000` on the native session.

## Done when
1. Given a new connection, the registry stores it wrapped in `ConcurrentWebSocketSessionDecorator` (limits from config, TERMINATE), and every ACK/ERROR/push goes through the wrapper; nothing writes to the raw session.
2. Given two threads writing to one session at once, both frames arrive intact, no `IllegalStateException`.
3. Given recipients A, B, C where B's socket blocks, C still receives, and B is closed with 4500 once > 512 KB buffered or a send is stuck > 5 s.
4. Given `SessionLimitExceededException` on a push, the emitter closes that session, the loop continues, nothing escapes to `SendMessageService`.
5. Given a native write stuck > the configured blocking-send timeout (5 s), it fails with an `IOException` and the session is closed.
6. Given any exit (normal close, transport error, TERMINATE), the registry entry and subscriptions are removed; cleanup twice is a no-op.
- **Out of scope:** per-frame NACK (T02), heartbeat/idle close (T03), shutdown close/drain (T14), serialize-once + moving fan-out (T07), registry reverse index (T08), real non-reading-client IT (T16).
- **Tests:** unit with a fake session whose `sendMessage` blocks on a latch (2–5); `ChatHandlerTest` for wrapping + every exit path (1, 6); existing WS ITs stay green.
- **Files:** `adapters/in/websocket/{handler/ChatHandler, session/SessionRegistry, session/FrameWriter, session/SessionEmitterAdapter}`, new WS properties (`config/`), ADR-0005 close-code list (`:53`).
- **Invariants:** no write to a raw session (`.claude/rules/websocket-protocol.md`); no authz change.

## Decisions
| Question | Answer | Source |
|---|---|---|
| Close code on overflow | 4500 (Spring's `SESSION_NOT_RELIABLE`) = "slow consumer → reconnect + resume"; amend ADR-0005:53 | user, 2026-11-26 |
| Bound the flushing thread | Tomcat `BLOCKING_SEND_TIMEOUT` = 5 s per native session | user, 2026-11-26 |
| Slow-consumer proof | Deterministic unit fake now; real raw-socket IT in T16 | user, 2026-11-26 |
| Limits | Config properties (5 s, 512 KB defaults) so tests use small values | `03-chat-system-design.md:157` |
