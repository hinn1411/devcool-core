# P3-T10 — Read state + unread count
P3 · mode A · Must · est 7h · agreed · 2026-11-13

**Why:** `member.last_read_seq` / `channel.last_seq` exist (`V4__message_seq_and_read_state.sql:8,17`) but no code reads or writes them; `ChannelListItem` (`domain/channel/model/ChannelListItem.java:6`) has no badge or preview data, and the list sorts by `c.id` (`ChannelRepository.java:56`).
**Value:** phase goal "Read state and unread counts". Unblocks P4-T04 (`READ` frame), P5-T04 (sidebar badge, preview, recency order), P8-T21 (catch-up from `last_read_seq`).

## Concepts
- **Unread as a subtraction:** without: 30 channels → 30 `COUNT(*)` over `message`. With: `last_seq − last_read_seq`, O(1), valid because seq is gap-free (P3-T03). Read: `docs/references/02-chat-system-design.md` (Read state).
- **Monotonic marker:** without: a stale tab sends 40 after the phone sent 55 → 15 messages unread again. With: one `UPDATE … SET last_read_seq = GREATEST(last_read_seq, LEAST(:seq, c.last_seq))`; the row lock makes it atomic.
- **Clamp to reality:** without: seq 9999 → future messages arrive "read", count goes negative. With: `LEAST(:seq, last_seq)`; a client never sees a higher seq (broadcast after commit).
- **Keyset on recency:** without: an id cursor under a `last_message_at` sort skips or repeats channels. With: cursor = `(last_message_at, id)`, `ORDER BY last_message_at DESC NULLS LAST, id DESC`.

## Done when
1. A member PUTs seq 5, then 3, then 5 → `last_read_seq = 5`; each call → 204.
2. Concurrent PUTs 5 and 8 → marker 8 in any order.
3. Seq > `last_seq` → clamped to `last_seq`; negative or missing seq → 422 (`ApiExceptionHandler.java:47`).
4. Non-member or unknown channel → 404, nothing written.
5. `GET /channels` item: `unreadCount = last_seq − last_read_seq`; `lastMessage` follows `ReplyPreview` rules (`domain/chat/model/ReplyPreview.java:9`: 100 code points, text `null` for media/deleted). No messages → `lastMessage: null`, `unreadCount: 0`.
6. A deleted message still counts as unread (`03-chat-system-design.md` §9).
7. A newly added member starts at `last_read_seq = channel.last_seq` → 0 unread (`MemberAdapter.java:44`).
8. Sending a message advances the sender's own marker in the send transaction → 0 unread for own sends.
9. List ordered by `last_message_at DESC NULLS LAST, id DESC`; paging with the opaque cursor across ties and empty channels returns each channel exactly once.
10. One channel page = one SQL statement (statement-count IT).
- **Out of scope:** WS `READ` / `READ_RECEIPT` (P4-T04), "seen by N", notifications (P6), a recency index (the member's channels are few; revisit at P9 load test).
- **Tests:** `ReadStateServiceTest`, `ChannelServiceTest` (list), `MessageServiceTest` (own-send marker), `ReadStateAdapterIT` (GREATEST, clamp, race), `ChannelAdapterIT` (order, cursor, statement count), `ChannelReadIT` (HTTP + 404 authz), `ChannelDtoMapperTest`.
- **Invariants / authz:** seq valid (422) → membership (404) → `0 ≤ last_read_seq ≤ last_seq`, never decreases.
