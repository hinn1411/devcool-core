## Concepts
- **MCP = docs lookup, not plan reading:** without: agent claims `aws_ecs_service` accepts a non-existent argument; caught only by CI `validate`. With: agent looks up provider/module docs and latest versions; the plan text still comes from `terraform plan` or the PR comment. Read: ref 16 § "MCP connects tools".
- **Subagent plan review:** without: a 600-line `app` plan fills the main context. With: `aws-architect` reads it in its own context and returns findings + a cost note. Read: ref 16 § "Subagents isolate context".
- **Plugin vs `.mcp.json`:** `enabledPlugins` in shared settings gives every clone the plugin's server; this one is `docker run hashicorp/terraform-mcp-server:0.4.0`, so Docker must be running.

## Done when
1. Given Docker is running, when a session starts, then `/mcp` shows `terraform` connected.
2. Given a stack (local `terraform plan`) or an infra PR number (`gh pr view <n> --comments`), when the user asks for a plan review, then `aws-architect` handles it and its report cites ≥ 1 Terraform MCP lookup, findings and a cost note.
3. Given Docker is stopped, when `aws-architect` runs, then it says the Terraform MCP is unavailable and falls back to `aws-knowledge`, not silent memory.
4. The review flags provider/module pins behind the latest registry version as Low (flag only, no bumps).
- **Out of scope:** bumping the plugin's image pin (upstream), HCP Terraform/TFE workspaces, CI-side Claude review (P0-T13 `claude.yml`).
- **Tests:** manual: `/mcp`; one review of a local `network` plan; one of an infra PR comment; repeat with Docker stopped.
- **Files:** `.claude/settings.json` (`enabledPlugins`), `.claude/agents/aws-architect.md` (description "use proactively for terraform plan output / infra PR plans", MCP use, pin check, unavailable fallback), `infra/CLAUDE.md`, phase-2 file (tick).
